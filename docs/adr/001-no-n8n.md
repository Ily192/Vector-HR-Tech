# ADR-001: Eliminar n8n; vibe-codear flows a FastAPI + Celery

- **Status:** Accepted
- **Date:** 2026-05-08
- **Decider:** Ilyra Rivas
- **Tags:** architecture, execution-layer

## Context

Existen 14 flujos n8n productivos para procesos HR (selección, crossboarding, constancias, psicométrico, sincronización Sheets/Supabase). Originalmente se planeó mantenerlos como adapters HTTP invocados por Paperclip.

Problemas observados:

1. JSONs no diff-eables → imposible code review.
2. Sin tests automatizados.
3. Vendor lock-in con n8n cloud o costo de self-hosting.
4. Latencia adicional (HTTP entre engine y n8n).
5. Nodos LLM aislados de los agentes (OpenClaw + Paperclip), duplicando lógica de cost tracking.
6. Difícil iteración con vibe coding (drag-drop UI).

Existe ya un repo en producción (`SDR-prospection`) que demuestra el patrón ideal: **FastAPI + Celery + Redis + workers en Python con estructura `_run()` async + `@celery_app.task` wrapper**.

## Decision

Eliminar n8n del stack. Migrar la lógica de los 14 JSON a workers Python en `services/hr-engine/app/workers/` siguiendo la convención de `SDR-prospection`. Cada worker tendrá:

- `async def _run(...)` testeable sin Celery.
- `@celery_app.task(name=...)` wrapper.
- Tests unit + integration por worker.
- Idempotencia obligatoria.
- Cost accounting integrado con Paperclip.

## Consequences

**Positivas:**
- Diff de cambios real en git.
- Tests automatizados.
- Sin dependencia de runtime externo.
- Vibe coding natural: copiar el patrón de un worker existente.
- Mismo runtime que agentes y cost tracking unificado.
- Latencia < 100 ms (in-process) vs ~500ms (HTTP n8n).

**Negativas:**
- Migración inicial: ~10 horas de trabajo (cycle 1 + parte de cycle 2).
- Pérdida temporal de la UI visual de n8n para debug — mitigado con dashboards Grafana de pipeline.

**Neutras:**
- Curva de aprendizaje Celery (mínima — un dev Python no especialista lo aprende en 1 día).

## Alternatives considered

| Alternativa | Por qué descartada |
|---|---|
| Mantener n8n | Acumula los 6 problemas listados arriba |
| Migrar a Temporal.io | Overkill para nuestra escala; complejidad operacional alta |
| Migrar a Airflow | Diseñado para ETL batch, no para pipelines reactivos < 5 min |
| Migrar a Prefect | Buen fit pero menos battle-tested en LATAM y curva mayor que Celery |
